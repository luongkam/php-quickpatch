## 1. Giới thiệu (Introduction)

### 1.1 Mục đích
Tài liệu chuyển 373 scenario Gherkin của bộ AC (DOC-AC-QP-000) thành test case chạy được cho php-quickpatch v2 (CLI Bash, console Python cục bộ, Phase 2 SSH), bổ sung test case cho quy tắc và mã lỗi chưa có scenario riêng, và truy vết FR → US → AC → TC theo rule 14 ([rtm.md](rtm.md)). Người đọc: QA (thực thi, báo lỗi), Dev (tái hiện lỗi), PO (nghiệm thu bản 2.0.0), kỹ sư bảo mật (bộ kiểm thử §5.1).

### 1.2 Phạm vi
- Phase 1, ưu tiên P0 và P1: 397 test case, thực thi trước phát hành 2.0.0 (P1 được lùi tối đa tới 2.1.0 theo backlog §2).
- Story mức epic P2 (`US-FEED-17`, `US-CMPT-11`, `US-UPG-15`): 9 test case, thực thi sau khi story được tách.
- Phase 2 (`US-FLT-01..05`): 15 test case ở mức đặc tả, chưa thực thi ở bản 2.0.0.
- Ngoài phạm vi: script tự động hoá (Playwright/Bruno) — bước `/playwright-gen`, `/api-test` sau; số liệu đo hiệu năng thực tế (NFR ghi "chưa đo" trong SRS).

### 1.3 Cấu trúc bảng test case (template 43 §2, rule 14)
| Cột | Nội dung |
| :--- | :--- |
| TC ID / Tên test case | Mã `TC-[MODULE]-NNN` và tên lấy từ tiêu đề scenario AC (hoặc tên test case bổ sung) |
| Story / AC | `US-*` và `AC-*` nguồn; test case bổ sung ghi `bổ sung (mở rộng AC-…)` |
| Loại | Loại kiểm thử chính (§1.4) · nhóm scenario hoặc nhóm bổ sung |
| Tiền điều kiện | Trạng thái hệ thống trước khi chạy (từ `Given`/`And` của AC); ký hiệu dùng chung giải thích ở §2.1 |
| Bước thực hiện | Hành động đánh số (từ `When`), bước cuối là thu bằng chứng và đối chiếu KQ |
| Dữ liệu test | Giá trị cụ thể cần chuẩn bị; Scenario Outline ghi đủ bảng dữ liệu, mỗi dòng là 1 lượt thực thi |
| Kết quả mong đợi | `KQn` đánh số (từ `Then`/`And`); test case Đạt khi 100% KQ đạt ở mọi dòng dữ liệu |
| BR / ERR kiểm | Mã `BR-*`/`ERR-*` trong registry SRS mà test case kiểm chứng; dùng để lập ma trận ở [test-cases-coverage.md](test-cases-coverage.md) |

### 1.4 Quy ước mã và loại kiểm thử
- Mã: `TC-[MODULE]-NNN`, `MODULE` trùng tiền tố story/AC (`SCAN`, `SCN`, `FEED`, `ASMT`, `PLAN`, `CMPT`, `PTCH`, `UPG`, `CON`, `JOB`, `CLI`, `RPT`, `FLT`). `NNN` = 001–099: ánh xạ 1:1 với `AC-[MODULE]-NN` cùng số (vd `AC-SCAN-01` → `TC-SCAN-001`); `NNN` = 101–199: test case bổ sung.
- Nhóm scenario theo tag AC: Happy path, Negative (có mã `ERR-*`), Boundary, Security. Nhóm test case bổ sung: Kịch bản phiên bản, Bổ sung BR, Bổ sung ERR, Bổ sung BR/ERR, Offline/Stale, Tự rollback, Bảo mật console.
- Loại kiểm thử chính (mỗi test case 1 loại):

| Loại | Tiêu chí xếp loại |
| :--- | :--- |
| Functional | Kiểm hành vi nghiệp vụ, quy tắc, trạng thái, giới hạn số của 1 chức năng trên máy kiểm thử |
| Security | Kiểm xác thực, phiên, Host, CSRF, danh sách trắng, header/CSP, toàn vẹn (SHA-256, chuỗi hash), che bí mật, quyền file; mọi scenario mang tag `@security` |
| Integration | Phụ thuộc hệ thống ngoài: nguồn online `SRC-*`, Packagist/npm registry, API/CLI panel, Docker Compose, SSH tới server khác |
| Compat | Tương thích ngược v0.1, hợp đồng `--json`/JSON Schema, phiên bản Bash/Python/OS, hồi quy dữ liệu ghi cứng |
| Rollback | Backup manifest, rollback lượt chạy, rollback site 1 lệnh, tự rollback khi health check thất bại |

### 1.5 Trạng thái thực thi và tiêu chí kết thúc
- Trạng thái mỗi lượt chạy: `Chưa chạy`, `Đạt` (100% KQ đạt), `Không đạt` (≥ 1 KQ sai, ghi lỗi kèm TC ID và KQ sai), `Bị chặn` (không dựng được tiền điều kiện, ghi lý do).
- Tiêu chí phát hành 2.0.0: 100% test case của story P0 Phase 1 ở `Đạt`; mỗi FR P0 có ≥ 1 test case `Đạt` (`NFR-MNT-004`); 0 test case loại Security ở `Không đạt`; test case P1 `Không đạt` được chấp nhận khi PO ghi nhận lùi sang 2.1.0.
- Chỉ tiêu ghi "mục tiêu, chưa đo" trong KQ (vd `NFR-PERF-004`, `NFR-PERF-005`, `NFR-CAP-002`, câu hỏi `Q-SRS-09` của SRS): kết quả đo được ghi vào báo cáo kiểm thử để cập nhật SRS 1.0.1, không chặn phát hành khi chưa có ngưỡng được PO duyệt.
